# MateView Guardian v0.2 GUI Design

## Goal

Replace the command-line-first experience with a self-contained GUI that runs from the macOS menu bar or Windows notification area, blocks every host media-control event from the faulty HUAWEI MateView GT touch strip, and maintains a user-selected internal monitor-speaker volume without interfering with normal operating-system, keyboard, application, or headphone volume controls.

The supported monitor is the HUAWEI MateView GT 34-inch Sound Edition identified as display model `ZQE-CAA` and USB HID vendor/product `0x12D1:0x10B6`.

## Supported setups

### macOS

- Apple Silicon Mac running macOS 13 or newer.
- MateView connected through the full-function USB-C port.
- The app blocks the MateView consumer-control HID usages with a device-specific `hidutil` mapping.
- The app maintains VCP `0x62` speaker volume through a bundled Apple Silicon DDC helper.

### Windows

- 64-bit Windows 10 or Windows 11.
- DisplayPort remains connected to the graphics card for 3440 x 1440 at 165 Hz and monitor audio.
- A second USB-C-to-USB-C data connection exposes the MateView HID interfaces to Windows.
- An elevated helper disables only HID instances whose IDs match `VID_12D1&PID_10B6`; it never disables the composite USB parent, microphone, another keyboard, or another monitor.
- The app maintains VCP `0x62` volume and VCP `0x8D` unmuted state through the native Windows monitor configuration API.

The Windows app remains useful with DisplayPort alone, but reports `USB data missing`; DDC protection continues while host HID protection is unavailable.

## Chosen architecture

Use a single Avalonia 12.1.1 application targeting .NET 10. The same view model, settings window, tray menu, configuration model, status model, watchdog policy, and tests are shared across platforms. Platform services isolate macOS process-based HID/DDC operations from Windows PnP and `Dxva2.dll` operations.

This is preferred over separate Swift and WinForms applications because it keeps behavior and UI consistent and avoids maintaining two settings and state systems. It is preferred over Electron because the app needs a small resident footprint and no browser runtime. Releases are self-contained, so users do not install .NET.

## Application structure

### Core

`MateViewGuardian.Core` contains no GUI or native calls. It owns:

- `GuardianSettings`: protection enabled, desired monitor volume `0...100`, start-at-login, selected monitor identity, and Windows HID instance IDs saved for recovery.
- `GuardianStatus`: disconnected, partially protected, protected, disabled, or error, plus individual HID and DDC messages.
- `CorrectionPolicy`: returns ordered DDC corrections only when the observed state differs from the target.
- `ProtectionCoordinator`: serializes checks, applies backoff after device failures, updates status, and prevents overlapping timer cycles.
- `IPlatformProtection`: detection, HID enable/disable, DDC read/write, and startup registration boundary.

Configuration is stored in the current user's application-data directory as JSON. Writes use a temporary file followed by an atomic replace. Invalid or corrupt configuration is preserved as `.invalid`, and safe defaults are loaded: protection enabled, volume `30`, start at login enabled.

### GUI and tray

`MateViewGuardian.App` supplies one small settings window and one persistent tray icon. Closing the settings window hides it; protection continues. Choosing Quit warns that protection stops, then exits cleanly.

The settings window shows:

- Overall protection toggle.
- MateView display and USB connection status.
- Separate HID block and DDC watchdog status.
- Internal speaker target slider and numeric value from `0` through `100`, default `30`.
- Start at login toggle.
- Apply Now, Diagnostics, and Uninstall/Restore controls.
- A permanent note that Huawei's firmware OSD and LED cannot be suppressed by host software.

The tray menu contains Show Settings, Protection On/Off, target-volume presets `20`, `30`, `40`, and `60`, Start at Login, Diagnostics, and Quit. Icon states are green for protected, yellow for partial/disconnected, red for error, and gray for disabled.

## Protection behavior

### Host HID blocking

On macOS, protection sets a `hidutil` mapping scoped to `VendorID 0x12D1` and `ProductID 0x10B6`. The four known consumer usages—volume up `0xE9`, volume down `0xEA`, play/pause `0xCD`, and pause `0xB1`—map to a no-op destination. The app verifies all four mappings every five seconds and reapplies after reconnect. Disabling protection clears only the matching MateView mapping.

On Windows, the non-elevated app enumerates matching HID instance IDs and passes only the exact allowlisted IDs to a bundled elevated PowerShell helper. The helper independently validates that every ID starts with `HID\\VID_12D1&PID_10B6` before calling `pnputil /disable-device` or `/enable-device`. Enabling protection may show one UAC prompt. The app records the disabled IDs so Disable, Uninstall, and Restore can re-enable them even while they are hidden from normal active-device enumeration.

The app never blocks HID devices globally. The user's MacBook keyboard, gaming keyboard, mouse, headset buttons, Bluetooth controls, and operating-system volume UI remain functional. The computer volume popup caused by the MateView should stop because the corresponding host events never arrive.

### DDC watchdog

The coordinator performs only one DDC transaction at a time.

- Read VCP `0x62` speaker volume.
- On Windows, read VCP `0x8D` mute state after the volume read.
- Compare values with the configured target.
- Write VCP `0x62` only when volume drifted.
- On Windows, write VCP `0x8D = 2` only when muted.
- Wait 500 ms after a complete successful cycle.
- On absence or communication failure, exponentially back off from 500 ms to at most 10 seconds and reset after the next complete success.

The Windows implementation reuses the tested `Dxva2.dll` monitor enumeration and requires a `ZQE-CAA` identity match. The macOS implementation invokes a bundled, pinned MIT-licensed AppleSiliconDDC helper, parses `detect` output to select only a service whose product name contains `ZQE-CAA`, and passes that exact IO display location to every read or write. The app does not use the helper's unqualified/default-display mode.

Normal operation never writes VCP `0xCA`, brightness, contrast, input selection, power state, or any code other than the platform-specific allowlist above.

## Startup, migration, and recovery

The app runs as the current user. macOS startup uses a per-user LaunchAgent pointing to the installed `.app`; Windows startup uses a current-user Startup entry. Neither startup mechanism requires elevation.

On first launch, the app detects the v0.1 macOS LaunchAgent or Windows watchdog files. It stops the old watcher after the GUI coordinator is running and preserves the existing target when available. The legacy command-line packages remain downloadable and their tests continue to run.

Protection Off performs recovery immediately:

- macOS clears the matching `hidutil` mapping and stops DDC correction.
- Windows stops DDC correction and requests elevation to re-enable every recorded MateView HID instance.

Uninstall performs Protection Off first, removes only the app's current-user startup/configuration files, and leaves the LED, monitor firmware, display settings, and unrelated devices untouched.

## Packaging and trust

GitHub Actions builds two self-contained assets:

- `MateViewGuardian-macOS-arm64.zip`, containing `MateView Guardian.app`, the DDC helper, third-party notices, and an install/uninstall helper.
- `MateViewGuardian-Windows-x64.zip`, containing the self-contained executable, HID helper, third-party notices, and uninstall helper.

The macOS bundle is ad-hoc signed for integrity but not Apple-notarized. The Windows executable is not Authenticode-signed. The README and first-run screen explain the resulting Gatekeeper or SmartScreen warning and link to source and checksums. No update service or telemetry is included.

## Error handling and diagnostics

- A missing monitor is a yellow disconnected state, not an error dialog.
- Missing Windows USB data is a yellow partial-protection state while DDC remains active.
- Denied UAC leaves HID protection off and explains how to retry; it does not claim full protection.
- DDC failures retain the last known values, use bounded backoff, and never trigger writes to another display.
- Diagnostics show app version, OS, display identity, HID identity/status, target volume, last successful DDC cycle, last correction, and sanitized recent errors. No usernames or full arbitrary device inventory are copied by default.

## Testing and release gates

- Core unit tests cover settings validation, corrupt-config recovery, status derivation, correction order, no-op cycles, serialization, and bounded retry.
- macOS tests use fake `hidutil` and DDC helpers to verify exact matching, command arguments, reconnect recovery, and forbidden-code rejection.
- Windows tests verify HID instance parsing/allowlisting, generated elevation commands, recovery of recorded IDs, exact display selection, and DDC code restrictions.
- GUI tests verify commands update settings/coordinator state and that window close hides rather than exits.
- Packaging tests inspect both archives for required runtime files, notices, executable bits where applicable, and absence of repository metadata.
- CI builds and tests on `macos-latest` and `windows-latest`; the macOS package receives a connected-hardware smoke test on the user's M1 Mac before release.
- Release `v0.2.0` is published only after all CI jobs pass and both uploaded archives download and pass checksum/archive-integrity verification.

## Known limitations

- The app cannot electrically disable the touch strip or LED controller.
- The Huawei firmware-generated volume OSD may still appear even though host volume changes and host volume UI are blocked.
- A new Windows USB topology can create a new HID instance ID and require another UAC approval to disable it.
- Apple Silicon DDC relies on private macOS interfaces used by existing open-source monitor tools and may require maintenance after macOS updates.
- The first public GUI release is unsigned/not notarized and therefore produces operating-system trust warnings.
